evpanda-node

A passive OCPI / OCPP capture SDK that lives inside someone else's production process. It records protocol traffic, buffers it in memory, and ships it in batches — while guaranteeing it never blocks, never throws, and never grows without bound.

This document explains how the SDK is put together, what happens to a captured message between your handler and the ingestion API, and how to wire it into a service. Read Part I and Part II to understand the machine; read Part III if you just need to use it.

The design tracks evpanda-go v0.3.0 — same layering, same pipeline, same wire records, same names wherever a TypeScript name can carry them. Where Node diverges it is deliberate, and §A lists every divergence in one place. This package was the original reference the Go and Python SDKs were ported from; what follows is the round trip back.

Part I

Architecture

1Constraints that shaped everything

This SDK is unusual in one respect: it runs inside a customer's charging platform, on their event loop, in their memory, on the hot path of their revenue-carrying traffic. Nothing it does is worth a degraded charging session. Four rules follow from that, and every design decision below is downstream of them.

Invariant 1

Capture never blocks. A capture call validates, copies, and pushes onto an array — no I/O, no await, nothing that can yield to the event loop. If the upstream is down, capture cost does not change.

Invariant 2

Nothing throws into the host. Every public entry point is wrapped. Capture methods return void, so an exception has nowhere to surface and is swallowed, counted, and (in debug) logged; flush and close never reject, and no promise the SDK creates can become an unhandledRejection.

Invariant 3

Memory is bounded, and the bound is a number you provision against. maxBufferBytes is the ceiling on everything held awaiting delivery — 32 MiB by default, allocated on demand. Under stress the SDK evicts rather than accumulating. The adapters add a second cost outside that ceiling, one bounded copy per in-flight request; §15.1 says why it is not folded in.

Invariant 4

A bad config degrades, it does not crash. startOCPI() / startOCPP() always return a usable client and never throw. A bad endpoint yields an inert client carrying the reason on .error; you may log it and carry on booting.

Two consequences are worth stating plainly, because they are the trade the whole design makes. Delivery is best-effort. A batch that survives five retries and still fails is dropped, and a buffer that fills evicts its oldest entries. Losing telemetry is always preferable to slowing down a charge point. And capture is fire-and-forget: no capture method returns anything, because there is nothing a caller could usefully do with a failure.

Why startOCPI() does not throw. Throwing is the JavaScript default, and for a library that computes something it is the right one. This library does not compute anything the host needs: if it cannot start, the correct outcome is a charging platform that boots without telemetry, not one that does not boot. So the failure is returned as state — panda.error, an Error instance you can instanceof-match or rethrow yourself — and it is logged on the way out, so ignoring the property is not the same as never being told.

2Shape of the package

One package, one entry point. Everything a consumer may use is re-exported from src/index.ts; nothing else is promised, and any of it can move without a breaking change. The build emits ESM, CJS and type declarations from that single entry, so a host on either module system gets the same surface.

The two protocols meet at one place: OCPIMessage and OCPPMessage are the only things the buffer holds, and sizeOf accounts for either. The transport maps them onto wire records through one type predicate — with exactly two message types and one call site, an interface would be indirection for its own sake.

2.1  Why the adapters sit apart, and why they need no peers

The capture pipeline and the adapters change at different rates. The pipeline is done — a buffer, a timer, a transport, and a wire contract that only moves when the ingestion API does. Adapters accumulate framework surface indefinitely. Keeping them in their own directory, behind one namespace export, means the growing half cannot crowd the finished half.

None of the three is a dependency, and that is deliberate. The express adapter is typed over node:http rather than express, so it works with connect, a bare http.createServer, or anything else that speaks (req, res, next). The fetch adapter takes the fetch implementation as an argument. The axios adapter imports axios as a type only, so the runtime bundle never references it. A host that installs this SDK installs nothing else.

client.ts — the seam the adapters consume
capturing(): number | undefined {
  // The per-body byte cap while this client is capturing, else
  // undefined. The cap and the fact of capturing come back together
  // deliberately: asked separately they could straddle a close and
  // disagree.
  return this.#worker?.config.maxCaptureBytes;
}

Go returns (maxCaptureBytes int, ok bool) and Python int | None; TypeScript says number | undefined, which is the same two facts in the shape the language already has for them. The adapters depend on a three-method Capturer interface rather than on OCPIClient, so they can be tested against a fake with no pipeline running.

What this replaced. An earlier revision passed the same two facts through an _internal property on the client, marked @internal and erased from the published typings by stripInternal. It worked, and it was the wrong trade: the adapters reached into a field the type system had been told to hide, so the seam existed but nobody outside could use it — and "write the capture call yourself" is the documented answer for a framework the SDK does not ship. A public method costs one line and makes that answer true.

3Concurrency model

One client owns one timer. Not a worker thread, not a pool — a timer, and it is unref'd, so it can never be the reason a process refuses to exit. It is the only thing in the SDK that performs I/O.

Node's single-threaded event loop is what makes the rest simple. The buffer needs no lock: a producer and the worker can never interleave mid-operation, because there is no mid-operation to interleave in. The Go SDK holds a mutex for the microseconds it takes to write a slot, and the Python one takes a lock on every counter increment; here both are free.

What the event loop does not give you. Serialization is free; non-reentrancy is not. A flush is asynchronous, so a second flush can begin while the first is awaiting a POST. That is what the single-flight promise in flushOnce is for — a concurrent caller joins the in-flight flush rather than starting a second one, which is the same guarantee Go gets structurally from its one goroutine and Python from a lock.

What is safe to call from where

flush() and close() are the two that wait, and they wait for as long as the transport's bounded retry takes. Neither belongs on a request path — capture is already asynchronous; you do not need to flush to make it happen.

Part II

Data flow

4The pipeline, end to end

Every captured message — OCPI or OCPP, adapter or direct call — takes exactly this path. There is no second route, no fast path, no bypass.

Two things are worth noticing about where the boundary sits. First, redaction happens above it — an unredacted message is never written to the buffer, so a heap snapshot of a running process cannot contain a captured Authorization header. Second, the capture timestamp is stamped above it too, at chokepoint time. captured_at is when your handler saw the traffic, not when the SDK got round to shipping it, so queue delay never distorts the record.

5The chokepoint

prepareOCPI and prepareOCPP in worker.ts are the single place a message is checked and transformed before it enters the queue. They are pure functions: given a message they return an envelope to enqueue, or undefined plus the reason it was dropped. Keeping them pure and module-local is deliberate — it means there is one answer to "why was my message not captured?", and it can be unit-tested without a client, a server, or a timer.

Four things happen there, in order:

  1. Validate the identity. OCPI needs id and name; OCPP needs id. Tenant is all-or-nothing — both tenantId and tenantName, or neither. A message the SDK cannot attribute is useless downstream, so it is dropped rather than shipped as an orphan.
  2. Enforce the byte cap. An oversize body drops the whole message, never a truncated one. Half a JSON body is unparseable, and worse, truncation could slice a credentials payload in a way that defeats the redactor below.
  3. Take ownership. Bodies are copied and header records shallow-copied, so the buffered capture shares nothing mutable with the host.
  4. Redact, then stamp capturedAt and wrap the message in its envelope.
types.ts — ownership is one function
export function ownBody(value: BodyInput | undefined): Uint8Array | undefined {
  if (value === undefined) return undefined;
  const bytes =
    typeof value === "string"
      ? new TextEncoder().encode(value)
      : Uint8Array.prototype.slice.call(value);   // copies
  return bytes.length === 0 ? undefined : bytes;
}

The copy is what makes the field safe to hand over. A capture is held until the next flush — up to flushInterval — so a body assigned straight from a reused buffer would be serialized after the host had already overwritten it. Silent, intermittent, and indistinguishable from an SDK bug. A Buffer handed to session.message() from a WebSocket library is exactly that case: ws reuses its read buffer.

OCPP has one extra rule. The ingestion contract requires both direction and raw_frame when event_type is 2 (MESSAGE), so a message event missing either is dropped at the chokepoint rather than being sent and rejected — a check this SDK did not have until this revision, and was quietly shipping 400-bound records without.

5.1  Redaction

Redaction is a closure built once per client, so the allowlist set is not rebuilt per message. OCPI has two rules:

  • Header allowlist. Only listed headers survive; every unlisted header is dropped, so Authorization, Cookie and X-API-Key fall off without needing to be enumerated. ocpiAllowedHeaders extends the list and can never shrink it. The default set is twelve headers, none of which can carry a secret. An allowlist rather than a denylist, because a denylist silently fails open when a partner invents a new auth header.
  • Credentials-token mask. The OCPI /credentials endpoint exchanges bearer tokens in the request body, where a header allowlist cannot reach. On a URL ending /credentials the token field is replaced with [redacted] — at the root for requests, under data for the response envelope. Any miss returns the original bytes unchanged: redaction never silently drops data it could not safely rewrite.

OCPP frames are captured verbatim, so there is no OCPP redactor at all: the client's redactor stays undefined and the chokepoint skips the step. The undefined-able argument is the seam — masking idTag in Authorize arrives as a makeOCPPRedactor plus one line in startOCPP, with nothing in the worker or the client to change.

6The buffer

A byte-bounded, drop-oldest queue. It does no I/O and knows nothing about protocols; it is a bounded handoff between many producers and one consumer.

Why bytes, not a message count. Captured messages vary by two orders of magnitude. A message count is a proxy for the thing an operator actually has to provision, and a poor one — the same 10 000 slots is ~3 MiB of OCPP heartbeats or 625 MiB of capped bodies. You cannot size a container against a number that is 100× off in the common case. This SDK shipped that slot count until this revision; maxBufferBytes is the number directly.

Drop-oldest rather than drop-newest is deliberate: during an incident the most recent frames are the ones an operator actually wants. The producer never learns that eviction happened — there is nothing useful it could do with that information, and returning an error would push a decision onto a caller who called a fire-and-forget method. The operator can act on it, which is what the counters in §12 are for.

Two implementation details keep the ceiling real. Evicted slots are cleared rather than left in place, because a live array slot keeps the whole body alive. And the live region is compacted once its evicted prefix reaches half the array — Array.shift is O(n) per eviction, so eviction-heavy traffic would otherwise pay for the whole queue on every message.

Accounting charges each message its variable-length parts plus a deliberately generous fixed overhead (256 B). Over-counting is the safe direction: it keeps the configured budget a true ceiling. The constant matches the Go and Python SDKs, so all three report comparable footprints for the same traffic.

7The worker

One unref'd timer, and no polling. The previous revision woke every 200 ms to check a counter — a workaround for a signal it always had. Node runs the producer and the timer on the same thread, so a producer that fills a batch can simply say so.

worker.ts — the producer side
private _enqueue(envelope: BufferedMessage): void {
  if (this._buffer.enqueue(envelope) < BATCH_CAP) return;
  if (this._stopped || this._inflight !== null) return;
  this._clearTimer();
  setImmediate(() => void this._tick());
}

setImmediate rather than an inline call is what keeps Invariant 1 intact: the capture returns first, and the flush runs on the next turn of the loop. A thousand producers arriving in one turn collapse into a single scheduled flush, because the second one sees an in-flight promise and returns.

7.1  Flush and drain

flushOnce installs a single-flight promise: a concurrent caller joins the in-flight flush rather than starting a second one. close stops the timers, awaits whatever is in flight, then drains the remaining buffer in a loop until it is empty or the deadline passes — and resolves to whether it managed it.

The deadline is passed down into the transport, not just checked between flushes. There is no way to cancel an in-flight fetch from outside without an AbortSignal, so the bound has to be respected by the code doing the work: the transport starts no attempt past the deadline, skips a backoff sleep that would cross it, and clamps each request's AbortSignal.timeout to the time remaining. That is what keeps close(2000) honest.

8The transport

Hand-rolled over global fetch. No generated client and no HTTP library: two endpoints do not justify putting a dependency — and its transitive tree, and its CVE feed — into a customer's production environment.

The transport owns retry entirely. The worker calls send once and moves on; there is no retry logic anywhere else, and no caller ever sees a delivery error.

KnobValueWhy
Batch cap1000The ingestion API's maxItems; also the size-based flush trigger
Max attempts5Bounded, so a dead upstream cannot hold the drain open indefinitely
Backoff500 ms → 30 sCapped exponential with full jitter, so restarts don't synchronize
Per-attempt timeout30 sA hung connection feeds the backoff instead of stalling the worker
Compression floor1024 BBelow this, compression costs more CPU than it saves bytes
Permanent statuses400 · 401 · 413Per the ingestion contract; everything else retries

None of these are configurable, and that is intentional. They are properties of the ingestion contract, not of a deployment, and every SDK must agree on them or the API's capacity planning stops meaning anything.

The codec is fixed, and it is free. zstd is the codec across all three SDKs, so a batch on the wire looks the same whichever language sent it. Node gained zstd in node:zlib at 22.15, which is why the engines floor is what it is — and why this package has no dependencies at all.

The previous revision reached for @mongodb-js/zstd, a native addon, as an optional peer with a gzip fallback. That meant a customer who skipped the optional install silently sent a different encoding than the other two SDKs. Node made both the dependency and the fallback unnecessary.

9Wire contract

Both endpoints take {"messages": [ … ]} with flat, snake_case records. The SDK's internal types are deliberately not the wire types, so the ergonomic TypeScript shape and the ingestion shape can evolve independently.

POST /v1/ocpi — one record
{
  "captured_at": "2026-08-30T09:14:22.418Z",
  "platform_id": "acme",
  "platform_name": "Acme Mobility",
  "tenant_id": null,
  "tenant_name": null,
  "direction": "IN",
  "http_method": "POST",
  "url": "/ocpi/2.2/cdrs",
  "response_status_code": 201,
  "request_headers": { "content-type": "application/json" },
  "request_body": "eyJpZCI6ImNkci0xIn0=",
  "response_headers": { "content-type": "application/json" },
  "response_body": null
}

Three conventions matter, and all three are shared with the other SDKs:

  • Absent means null, never a zero value. A missing status code must serialize as null, not 0 — the difference between "no response" and "status zero" is real, and a dropped key would make it invisible.
  • Bodies are base64, always. Both OCPI HTTP bodies and OCPP wire frames. The ingest server decodes before persistence, so downstream consumers see plain UTF-8; encoding keeps the contract uniform across protocols and binary-safe.
  • Timestamps are RFC 3339, UTC, millisecond precision — which is exactly what Date.toISOString() produces.

The Platform rename does not touch any of this: platform_id and charger_id are still the JSON keys, and the wire-shape tests pin them.

Durations are milliseconds, which is what setTimeout and every other Node API speak. Go uses time.Duration and Python float seconds; each SDK uses the unit its runtime already speaks, and the defaults are the same wall-clock values in all three.

Config resolution is also where a JavaScript SDK has to be more defensive than a Go one. Nothing stops a caller passing a string where a number belongs, and TypeScript types are gone at runtime, so each tunable checks its own type, falls back to the default, and says so — through a sink that swallows exceptions from the host's own logger, because a broken logger must not be able to fail config resolution.

11Lifecycle

the whole lifecycle surface
const panda = startOCPI(config);   // never throws, always usable
if (panda.error) {                 // a ConfigError instance, or undefined
  log.warn(`${panda.error.message} (running inert)`);
}

await panda.flush();               // deliver now, wait for it
const drained = await panda.close();       // drain within drainTimeout
const drained2 = await panda.close(30_000); // …or your own deadline

An inert client is a real client. When start* fails it returns a client with no worker. Every capture method is a no-op, flush() resolves immediately, close() reports a clean drain, connection() still hands back a usable session, and the adapters fall back to serving requests untouched. This is why the constructor returns a client plus an .error rather than throwing: a telemetry SDK must never be the reason a charging platform won't boot.

Close is idempotent, and post-close captures are safe. The client drops its worker reference, so the second close() resolves to the first call's answer. A capture that arrives after close finds no worker and returns. Both are ordinary, expected paths — not error conditions.

The resolved value means drain, not delivery. close() resolves to false when the deadline expired with messages still buffered — meaning some telemetry was dropped on the way out. It does not report delivery failures, which are retried and dropped by design. For those, set logMode: "debug" or read stats().droppedUndeliverable.

The timer is unref'd, which cuts both ways. A pending flush can never hold a process open — which is what you want from a telemetry SDK, and is why a short-lived script exits when it is done rather than five seconds later. The cost is that an unclosed client loses whatever it captured since the last flush. Python installs an atexit drain for the same problem; Node has no equivalent hook that can await, so this one is a documented close() in your shutdown path.

12Knowing whether it's working

The SDK discards data in five places by design, and four of them were invisible — which made the single most likely integration bug, an adapter that never resolves an identity, look exactly like a working SDK on an idle system. No error, no log, no signal, and a support ticket that could not be answered.

12.1  Counters

stats() is always available: no log mode turns it off, and it is safe on an inert or closed client (a closed one reports its final totals). The counters live on the client rather than the worker precisely so the lifetime tally survives close().

CounterWhat a high value means
captured = 0The capture path is not wired in
droppedInvalidIdentity resolution is failing
droppedOversizeBodies exceed maxCaptureBytes
droppedEvictedUpstream can't keep up, or maxBufferBytes is too small
droppedUndeliverableNetwork, API key, or ingestion fault
droppedFaultA bug in the SDK

One counter per root cause is the whole design goal: it turns an open-ended investigation into a lookup, in production, with no redeploy. It is a pull-based snapshot rather than an emitter, so it composes with Prometheus or OpenTelemetry without the SDK depending on either.

12.2  Logging is on by default, and rate-bounded

The policy, and the hazard it avoids. A silent SDK that captures nothing is indistinguishable from a working one, so the default is not silence — problems are reported without the host switching anything on. This SDK previously defaulted to debug: false, which meant total silence.

What makes the new default safe is that the SDK logs the rate, not the event. An adapter that resolves no identity drops on every request; per-event logging would emit at request rate, flood the host's log pipeline, and cost them real money in ingestion fees. Instead: one summary line per minute, carrying everything that happened in the window.

Leaving logMode unset consults $EVPANDA_LOG, which is the point: an operator can silence the SDK mid-incident with a restart rather than a code change. An explicit field wins over the environment — matching how apiKey resolves — and anything unrecognised in either falls back to errors; a typo must not be able to silence the SDK.

13OCPP

OCPP identity is known at connect time — you authenticated the charge point during the handshake — so there is no resolver. The recommended path is a session handle: it mints the connection ID, records the connect, and carries the identity, so per-frame calls carry neither.

a CSMS WebSocket handler
import { startOCPP } from "@evpanda/sdk";

const panda = startOCPP();
if (panda.error) log.warn(`${panda.error.message} (running inert)`);

wss.on("connection", (socket, req) => {
  // Your own charge-point identification — whatever your CSMS already
  // does at handshake time: parse the path, read Basic auth, check a
  // client certificate, hit your database.
  const charger = resolveCharger(req);
  if (!charger) return socket.close(1008);

  const session = panda.connection(charger);   // records the connect

  socket.on("message", (frame) => {
    session.message(frame.toString(), "FROM_CP");

    const reply = handleFrame(frame);          // your CSMS logic
    socket.send(reply);
    session.message(reply, "TO_CP");
  });

  socket.on("close", () => session.disconnect());  // records the close
});

Frames may be a string or a Uint8Array — a WebSocket library hands you either depending on whether the frame was text or binary, and both are normalized at the chokepoint. Note that ws reuses its read buffer, which is exactly why the chokepoint copies (§5).

14OCPI, directly

OCPI traffic flows both ways between roaming partners, and the SDK records each direction separately. The method name sets the direction — there is no direction field to pass, and no way to get it backwards.

MethodYou are the…Typical case
captureInboundMessageserverAn eMSP pushes a CDR or session update to your endpoints
captureOutboundMessageclientYou pull a partner's locations, or post a token authorization

Easy to get wrong. Identity is always the partner on the other side of the exchange — never your own platform. Inbound and outbound both. A record attributed to yourself is not wrong at the API, it is just useless.

direct capture
panda.captureInboundMessage({
  identity: { id: "acme", name: "Acme Mobility" },
  data: {
    method: "POST",
    url: "/ocpi/2.2/cdrs",
    statusCode: 201,
    requestHeaders: { "content-type": "application/json" },
    responseHeaders: { "content-type": "application/json" },
    requestBody,
    responseBody,
  },
});

Use this path when you have identity in hand and the adapters do not fit — a framework the middleware cannot wrap, or a replay from an audit log.

15OCPI adapters

The adapters do the assembly for you: collect headers and bodies, resolve identity, call the right method. Three of them, one per HTTP layer a Node service is likely to speak, and none of them a dependency.

AdapterDirectionWrapsNeeds
ocpi.express(client)inboundexpress, connect, bare node:httpnothing
ocpi.fetch(client, fetch)outboundany fetch implementationnothing
ocpi.axios(client, instance)outboundan axios instanceaxios (type-only)

That last point is the one real divergence from the Go adapters. Go carries identity on a context.Context, which is immutable — a value stamped inside the handler cannot be read by the middleware around it, so ocpi.Middleware must be mounted after auth. A Node request object is a mutable object shared with everything downstream, so the adapter reads identity at the end of the request and the ordering problem disappears.

The express adapter tees res.write and res.end for the response body, and reads the request body from req.body — whatever a body parser populated. It never tees the raw request stream, because attaching a 'data' listener would flip it to flowing mode and could starve the host's own parser. express.raw() yields exact bytes; express.json() a re-serialized form. It ships on both 'finish' and 'close', so an aborted exchange is captured too, and it never ships twice.

The fetch adapter clones the request and the response so the caller's streams stay intact, and reads the clones in the background — the caller has its response already and never waits on capture. The axios adapter uses a request and a response interceptor, stashing what it needs on the config between them; it captures non-2xx responses through the error interceptor too, since a 404 from a partner is exactly the exchange you want.

All three make exactly one change to a request: they strip the SDK's X-EVPanda-* identity headers before dispatch, so a partner never receives them and your tenantId / tenantName stay internal. Stripping happens even on a closed client, so closing mid-flight cannot start leaking them.

15.1  What the adapters cost in memory

maxBufferBytes is the ceiling on everything awaiting delivery. The adapters sit outside it: while a request is in flight they hold a copy of its bodies, bounded per request by maxCaptureBytes and released the moment the exchange is captured. The cost scales with concurrency rather than with the buffer, and with the bodies that actually pass rather than with the cap. Capturing by hand instead of through an adapter avoids it entirely, since the caller already holds the bytes.

Why it is not folded into the ceiling. A shared budget across in-flight requests is only enforceable one way: when it is exhausted, something has to wait for it. That is a request waiting on the telemetry SDK, which Invariant 1 forbids outright.

16Identity resolution

All three adapters resolve identity the same way, and the order is the point.

Three carriers, because Node hands you three different places to put a value and no single one covers them all:

  • The request object — where an auth layer already has the partner in hand. setIdentity(req, platform) and identityFrom(req) are the helpers. It is the same object the adapter reads at the end of the request, which is what makes mount order irrelevant.
  • An AsyncLocalStorage scope, through useIdentity(platform, fn). This is the carrier for code with no request object to stamp — an outgoing call, most obviously. It follows the async call chain rather than leaking to whatever else the event loop is running, which a module-level variable would.
  • The X-EVPanda-* headers, for hosts whose identity is already stamped by an upstream proxy or a different process. This was the only carrier before this revision, which meant an express host had to inject headers onto a partner's own request to attribute it.

If identity lives somewhere none of the three reach — a client certificate, a path prefix, your own session store — replace the shipped resolver with { resolve }. It takes a RequestInfo: method, URL, lowercased headers, whatever the adapter's own carrier held, and the framework-native object in context for anything else it needs. A resolver that throws is treated as "no identity"; the request is served normally either way.

BKnown gaps and open questions

Recorded so they are decisions rather than oversights.

Spec disagreement. response_status_code is in the ingestion spec's required list but is not marked nullable — yet all three SDKs send null when the status is absent. If Atlas validates strictly, an OCPI capture without a status code will be rejected. Node matches Go here because Go is the reference, but the spec and the SDKs disagree and one of them should move.

  • The express adapter needs a body parser. It reads req.body rather than teeing the raw stream, because a 'data' listener would flip the stream to flowing mode and could starve the host's own parser. A route with no parser records no request body. Go tees r.Body and Python reads it up front; this is the one place the three differ on inbound bodies, and it is a consequence of Node streams, not a choice about capture.
  • A transport failure produces no capture. DNS, refused, timeout — there is no exchange, so nothing is recorded. For a roaming platform "partner endpoint unreachable" is real signal, and all three SDKs are blind to it. Capturing it needs an SDK entry point and the response_status_code nullable fix above, so it is a cross-SDK change rather than a Node one.
  • OCPP redaction is a seam, not a feature. Frames are captured verbatim today. idTag in Authorize is the obvious first candidate.
  • No Fastify or Koa adapter. Fastify's hooks and Koa's middleware signature both differ enough from (req, res, next) to need their own. The Capturer seam is public precisely so one can be written outside this package (§2.1).
  • The counters stay inside the process. §12 makes drops visible to whoever runs the host — but EVPanda's own ingestion API still cannot tell a broken integration from an idle one. Piggybacking the counters onto the ingest request would let the dashboard flag a customer whose identity resolution is failing without them lifting a finger. It needs an ingestion contract change, so it is a follow-on — but it is where the counters are heading.
  • One client per protocol per process is assumed. Running many (per tenant, say) works, but each carries its own timer and buffer — the memory bound multiplies.
